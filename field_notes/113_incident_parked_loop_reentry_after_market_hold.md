## Critical Correction

This was not simply a case of:

```text
harsh critique → bounded README asset → successful compounding
```

The correct sequence was:

```text
Grok gave a blunt market critique of Entry Window Radar.
Entry Window Radar was judged too early or too weak to become the current flagship.
The working direction shifted toward planning the next thing to build.
During that transition, the workflow was pulled back toward an Entry Window Radar video.
The Decision Owner felt Resource Justice friction: if the repo was going to be parked or quiet, spending more time on a video felt wasteful.
The work paused.
On the next morning, re-entry failed because context, sync, or handoff state was unstable.
The OpenMontage/video branch was eventually salvaged, but the accident pattern matters more than the output.
```

## Incident Pattern

The incident pattern is:

```text
A loop that had effectively moved into HOLD / parked status was reopened without an explicit Re-entry Gate.
```

The problem was not that the video was useless.

The problem was that the return to the parked loop did not clearly answer:

```text
Why are we returning?
What is the bounded scope?
What will not be reopened?
What completion line closes the return?
Does this protect or consume the Decision Owner’s remaining resources?
```

Without those answers, a return-to-loop can feel like strategic backtracking even if the local task is directionally useful.

## Resource Justice Friction

Resource Justice friction appeared because the Decision Owner had already accepted that Entry Window Radar should not be treated as the current flagship.

Returning to video production created a conflict:

```text
If this project is being parked, why are we spending more scarce attention on making a video for it?
```

This is not ordinary reluctance.

It is a valid V14 signal.

A parked loop can still receive a bounded maintenance action, but only if the reason, scope, and closure are explicit.

## Small Failures Observed

The workflow included small failures that increased friction:

```text
AI proceeded as if it inherited context it did not actually inherit.
OpenMontage context was misconnected to Entry Window Radar video explanation.
Unnecessary options were returned to the Decision Owner.
A separate route was proposed while render work was still active.
The Decision Owner’s judgment resources were consumed by avoidable branch handling.
```

These failures did not destroy the project.

However, they became more costly because they occurred during re-entry into a loop that was already psychologically and strategically parked.

```text
A useful salvage does not erase the re-entry accident that made the salvage necessary.
```

## Parked Loop Re-entry Gate

When a loop has already been market-HOLDed, parked, or deprioritized, returning to it requires an explicit Re-entry Gate.

Minimum gate questions:

```text
Why are we returning to this parked loop?
What is the bounded scope of the return?
What will not be reopened?
What completion line closes the return?
What resource does this protect?
What resource might this consume?
Who keeps the Seat?
What is the next action after closure?
```

If these cannot be answered, the return should default to HOLD.
